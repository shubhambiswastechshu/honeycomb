{% load i18n %} {% comment %} Replaces the admin's 275px text sidebar with the app's icon rail, so crossing from /dashboard into /admin does not change what navigation looks like. Four things follow from that and are deliberate: * The id is `hc-rail`, not `nav-sidebar`. Django's nav_sidebar.js looks up `#nav-sidebar` and then `#nav-filter` unconditionally; renaming the element makes that script bail on its first lookup instead of throwing on a filter box this rail does not have. It also frees the rail from nav_sidebar.css, whose every rule is keyed on that id. * There is no toggle. The rail is a fixed column of icons -- there is nothing to reclaim by collapsing it, and a chrome element that can vanish is one the eye has to re-find on every page. * **Labels are on screen, not in a tooltip.** This matches components/dashboard/IconRail.tsx and for the same reason: an icon-only rail works when every glyph is unambiguous, and a dozen admin models are not. "Connections", "Connector OAuth states", "MCP keys" and "MCP activity" are four abstractions no icon distinguishes on its own, so the name belongs next to the icon rather than behind a hover a keyboard user never triggers. The CSS tooltip this rail used to carry is gone with it -- `title` says more than it did, because it names the app as well, and `aria-label` carries the name to assistive tech. * **One list per app, separated by a hairline.** `available_apps` arrives grouped already, and flattening it threw that away -- twelve items in one undifferentiated column is a list to read, whereas five short groups is a structure to scan. The group is the only thing that distinguishes, say, the crawler's four tables from the MCP portal's two. `available_apps` comes from AdminSite.each_context, so this works on every admin page without a view change. {% endcomment %} {% url 'admin:index' as admin_index_url %}
